# Cognitive Memory LLM Service

A FastAPI service that gives a chat assistant **long-term memory**. It turns what a user says into small atomic facts, stores them in a vector store (ChromaDB) and a knowledge graph (PostgreSQL), and pulls the relevant ones back out to ground each LLM reply (Groq).

It is the Python "brain" of the **AI Cognitive Memory** system. A Spring Boot API sits in front of it and calls it over HTTP with a shared bearer token. The React frontend never talks to this service directly.

> 📘 **Full project documentation:** [docs/DOCUMENTATION.md](docs/DOCUMENTATION.md)
> It covers the architecture, every endpoint with request and response examples, the memory pipelines, the database schema, tuning constants, testing and troubleshooting.

---

## Features

- **Atomic fact extraction.** `"My name is Rushabh and I work at Yardi"` becomes two facts, each classified (domain, status, importance) in one LLM call. Questions are never stored as facts.
- **Vector memory.** Facts are embedded with `all-MiniLM-L6-v2` and stored in ChromaDB, isolated per user. Retrieval can be narrowed to a domain.
- **Knowledge graph memory.** Each fact also becomes a PostgreSQL graph node with domain, sub-domain, status (`ongoing`/`completed`), timeline and importance, linked by `RELATED_TO` / `LED_TO` edges.
- **Fact revision and task progression.** "My favorite player is now Virat Kohli" archives the old value as history instead of keeping both. "I got the offer" marks the matching ongoing task as completed.
- **Duplicate cleanup.** A background pass clusters nodes that describe the same thing and archives the duplicates. Nothing is deleted.
- **Rolling summaries.** A scheduler builds a per-user digest (active goals, recent completions, standing facts) when the service is idle.
- **Memory-aware chat.** `/ai/chat` puts the current session's turns ahead of long-term memory in the prompt, so a recent message always wins over an older memory.
- **Graceful degradation.** Graph processing runs in the background, so a graph or LLM failure never breaks storing a memory or chatting.

## Architecture

```
React frontend ──JWT──► Spring Boot API ──Bearer token──► this service (FastAPI :8000)
                                                            │
                         ┌──────────────────────────────────┼─────────────────────┐
                         ▼                                  ▼                     ▼
                  ChromaDB (./chroma_data)         PostgreSQL graph tables     Groq LLM API
                  vector memories                  graph_nodes / graph_edges
                                                   user_summaries
```

See [Architecture](docs/DOCUMENTATION.md#2-architecture) for the full request flow.

## Tech stack

| Area | Technology |
|---|---|
| API | FastAPI, Uvicorn, Pydantic |
| LLM | Groq (`GROQ_MODEL` for chat, `FAST_LLM_MODEL` for extraction) |
| Embeddings | sentence-transformers `all-MiniLM-L6-v2` (384 dimensions) |
| Vector store | ChromaDB (persistent, on disk) |
| Graph store | PostgreSQL via psycopg2 (threaded connection pool) |
| Scheduling | APScheduler (in-process) |
| Cache (optional) | Redis embedding cache, off by default |

## Quick start

### Prerequisites

- Python 3.10 or newer
- PostgreSQL running and reachable. The database named in `DB_NAME` must exist; the service creates its own tables on startup.
- A Groq API key from [console.groq.com](https://console.groq.com)

### 1. Install

**Windows**

```bat
setup.bat
```

**Linux / macOS**

```bash
chmod +x setup.sh
./setup.sh
```

Each script creates `venv/`, installs `requirements.txt` and copies `.env.example` to `.env` if `.env` doesn't exist yet.

To do it by hand instead:

```bash
python -m venv venv
venv\Scripts\activate          # Windows
source venv/bin/activate       # Linux / macOS
pip install -r requirements.txt
cp .env.example .env
```

### 2. Configure

Open `.env` and fill in at least these values:

```env
GROQ_API_KEY=your-groq-key
API_BEARER_TOKEN=a-long-random-secret     # must match the Spring Boot config
DB_PASSWORD=your-postgres-password
```

The server refuses to start if `GROQ_API_KEY` or `API_BEARER_TOKEN` is missing. All variables are listed in [Configuration](docs/DOCUMENTATION.md#4-configuration).

> The setup scripts still print "fill in ANTHROPIC_API_KEY". That message is out of date: the service uses `GROQ_API_KEY`.

### 3. Run

```bash
uvicorn main:app --port 8000
# or
python main.py
```

The first start downloads the embedding model (about 80 MB). Run a **single worker**: the summarization scheduler keeps its load tracking in process memory.

### 4. Check it works

```bash
curl http://localhost:8000/health
```

Interactive API docs are generated by FastAPI at **http://localhost:8000/docs** (Swagger UI) and **http://localhost:8000/redoc**.

## API at a glance

Every endpoint except `/health` needs `Authorization: Bearer <API_BEARER_TOKEN>`.

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/memory/store` | Split a message into facts and store them |
| `POST` | `/memory/retrieve` | Semantic search over a user's memories |
| `GET` | `/memory/all/{userId}` | List every stored memory for a user |
| `DELETE` | `/memory/{userId}` | Delete a user's memories from both stores |
| `POST` | `/ai/chat` | Generate a memory-aware reply |
| `GET` | `/health` | Dependency health check (no auth) |
| `POST` | `/graph/process` | Add one memory to the knowledge graph |
| `POST` | `/graph/context` | Scored graph context for a query |
| `GET` | `/graph/summary/{userId}` | Latest rolling summary |
| `GET` | `/graph/history/{userId}` | Revision history of changed facts |
| `GET` | `/graph/timeline/{userId}` | Memories grouped by month, domain and status |
| `POST` | `/graph/status-update` | Set a node to `ongoing` or `completed` |
| `GET` | `/graph/all` | Admin view of every node, across all users |
| `DELETE` | `/graph/{userId}` | Delete a user's graph only |

Request and response examples for each are in the [API reference](docs/DOCUMENTATION.md#5-api-reference).

### Example

```bash
curl -X POST http://localhost:8000/memory/store \
  -H "Authorization: Bearer $API_BEARER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"userId": "42", "text": "My name is Rushabh and I work at Yardi", "role": "user"}'
```

```json
{ "status": "stored", "ids": ["42_1759400000_a1b2c3d4", "42_1759400000_e5f6a7b8"], "facts_count": 2 }
```

## Project structure

```
cognitive-memory-llm-service/
├── main.py                     App entry point: core endpoints, auth, middleware, background graph task
├── graph_routes.py             /graph/* endpoints
├── config.py                   Environment configuration and startup validation
├── models.py                   Pydantic request/response models
├── ai_service.py               System prompt construction and the chat LLM call
├── atomic_extractor.py         Fact splitting, classification and quality filters
├── embeddings.py               Sentence-transformer model and optional Redis cache
├── memory_store.py             ChromaDB access (the only module that touches it)
├── graph_memory.py             Knowledge graph in PostgreSQL: matching, revision, merging, scoring
├── summarization.py            Rolling per-user summaries
├── scheduler.py                Low-load-gated background scheduler
├── backfill_legacy_domains.py  One-off script that tags old memories with a domain
├── tests/
│   └── test_fact_regressions.py  Live regression tests (real Groq + PostgreSQL)
├── setup.bat / setup.sh        Environment bootstrap
├── requirements.txt
└── .env.example                Template for every environment variable
```

## Testing

```bash
python tests/test_fact_regressions.py
```

These are live tests. They call the real Groq API and write to PostgreSQL under a throwaway user that is deleted afterwards. ChromaDB writes go to a temporary directory, so your real vector store is never touched. Tests skip, rather than fail, when the config, database or LLM quota is unavailable. See [Testing](docs/DOCUMENTATION.md#10-testing).
